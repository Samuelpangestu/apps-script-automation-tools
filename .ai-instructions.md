# Instructions for AI Assistants

This document contains important instructions for AI assistants working with this repository.

## Environment Management

### Testing vs Production

This repository uses **TWO separate Apps Script projects** for each component:

1. **Testing Environment** (Default)
   - For development and testing
   - `.clasp.json` points here by default
   - Safe to experiment and test changes

2. **Production Environment**
   - Live system used by QA team
   - Requires explicit user confirmation to deploy
   - Must be stable and tested

See [ENVIRONMENTS.md](./ENVIRONMENTS.md) for complete list of script IDs.

### Deployment Rules for AI

**DEFAULT BEHAVIOR:**
- Always deploy to **Testing ONLY** unless explicitly told otherwise
- Use `./deploy-testing.sh` script when available

**When user says "push to production":**
1. Use `./deploy-production.sh` script (has built-in confirmation)
2. OR manually change scriptId in `.clasp.json`
3. Run `clasp push`
4. **IMPORTANT: Revert `.clasp.json` back to testing scriptId**

**When user says "push to both" or "deploy to testing and production":**
1. Use `./deploy-all.sh` script
2. OR deploy to testing first, then production
3. Always revert `.clasp.json` to testing at the end

## Deployment Workflow

### Preferred Method (Using Scripts)

```bash
cd projects/qa-dashboard

# Deploy to testing
./deploy-testing.sh

# Deploy to production (asks for confirmation)
./deploy-production.sh

# Deploy to both
./deploy-all.sh
```

## Dashboard Calculation Ownership

- Keep dashboard/business calculations in Google Sheets / Apps Script. History and Bugs tabs should store pre-calculated values such as pass rate, execution rate, automation coverage, health score, and production severity/status breakdowns.
- Next.js should only map, render, filter, and sort values that already exist in the sheet/API response. Do not add proportional fallback calculations in the UI.
- Project/module/submodule additions or removals should be handled by Apps Script aggregation so downstream dashboards remain maintenance-light.
- Use modern, actively maintained dependencies and patterns while preserving the existing clean operational dashboard layout.

### Manual Method (Fallback)

```bash
cd projects/qa-dashboard

# For testing
clasp push

# For production
# 1. Edit .clasp.json - change scriptId to production
# 2. clasp push
# 3. Revert .clasp.json back to testing scriptId
```

## Common Tasks

### Making Changes

1. **Edit files** in `src/` directory
2. **Test locally** in testing spreadsheet
3. **Deploy to testing** using `./deploy-testing.sh`
4. **Verify** changes work correctly
5. **Deploy to production** (only when user confirms)

### Adding New Features

1. **Always test in Testing environment first**
2. **Document changes** in commit messages
3. **Update README** if adding new functionality
4. **Get user approval** before deploying to production

### Troubleshooting Deployments

If deployment fails:
1. Check `clasp login` status
2. Verify script ID is correct
3. Check for authentication errors
4. Read error message carefully

## Safety Rules

1. ✅ **DO** test in testing environment first
2. ✅ **DO** use deployment scripts when available
3. ✅ **DO** revert `.clasp.json` to testing after production deploy
4. ✅ **DO** ask for confirmation before production deploy

5. ❌ **DON'T** deploy to production without user confirmation
6. ❌ **DON'T** leave `.clasp.json` pointing to production
7. ❌ **DON'T** commit `.clasp.json` with production scriptId
8. ❌ **DON'T** skip testing when making changes

## Questions to Ask User

If unclear which environment to deploy to, ask:
- "Should I deploy to testing only, or production as well?"
- "Have you tested this in the testing environment?"
- "Are you ready to deploy to production?"

## Context Awareness

When starting a new conversation:
1. **Check `.clasp.json`** to see current environment
2. **Read ENVIRONMENTS.md** to get script IDs
3. **Assume testing by default** unless told otherwise
4. **Look for deployment scripts** before manual deployment
