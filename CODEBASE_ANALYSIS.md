2. **Column G (Spreadsheet ID)** is not empty AND
3. **Spreadsheet ID** is ≥ 10 characters AND
4. **Spreadsheet ID** ≠ "PASTE_SPREADSHEET_ID_HERE"

### Jira Sync Flow

**Step 3: Sync Execution** (`_syncMod_()`)


### Duplicate Prevention Mechanism

**Current Approach: FULL REPLACEMENT (NOT incremental)**

```javascript
function _syncMod_(mod, cred, inclStatus) {
  // Step 1: Clean all existing data (keep header rows 1-4)
  _cleanBugReportData_(bugSh);  // ← CLEARS ALL ROWS EVERY SYNC
  
  // Step 2: Fetch bugs from Jira
  const issues = _fetch_(mod.inst, mod.projKey, mod.module, cred);
  
  // Step 3: Insert all bugs (skip Closed/Won't Fix)
  issues.forEach(iss => {
    _ins_(bugSh, iss, instUrl, now, mod, mod.inst);
  });
}
```

**How it Works:**
1. Every sync, ALL data rows are cleared (using `clearContent()` instead of `deleteRows()`)
2. Fresh bugs are fetched from Jira
3. Closed/Won't Fix bugs are filtered out (not inserted)
4. Each bug is inserted as a new row with unique Jira key

**Advantages:**
- No duplicate tracking needed (all data is fresh each sync)
- Automatically handles Jira status changes (closed bugs disappear)
- Simple and reliable

**Potential Gaps:**
- If a bug is manually edited in the sheet (e.g., Notes, TC columns), those edits are lost on next sync
- Manual rows cannot be preserved
- No partial sync capability

### Common API Pattern in Codebase

```javascript
// 1. Get credentials from Config/Credentials sheet
const cred = _getCreds_(ss);  // Returns { email, token } per instance

// 2. Build request
const url = baseUrl + '/rest/api/3/search/jql?jql=' + encodeURIComponent(jql);

// 3. Execute with error handling

  Logger.log('Fetch error: ' + e.message);
  return null;
}

// 4. Check status and parse
```

**Error Handling Strategy:**
- Use `muteHttpExceptions: true` to prevent script termination
- Check HTTP status code
- Log all URLs and JQL queries for debugging
- Return `null` on error (calling code handles gracefully)
- Never throw exceptions from API calls (use fallback values)

## 6. DUPLICATE PREVENTION & SYNC TRACKING

### Bug Report Sync Tracking

**Column W (SYNCED)** contains timestamp of last Jira sync.

```javascript
row[BC_.SYNCED-1] = now;  // ISO format timestamp
```

**Current Limitation:**
- SYNCED timestamp is overwritten every sync
- No historical tracking of when a bug was first added
- Only useful for knowing "last time Jira was synced"

### Bug ID Uniqueness

**Primary Key:** Jira Key (Column A)
```javascript
row[BC_.BUG_ID-1] = key;  // e.g., "TEST-3017"
row[BC_.JIRA_KEY-1] = key;  // Duplicate, but hyperlinked differently
```

**Why full replacement works:**
1. Every sync, ALL rows cleared
2. Jira returns authoritative bug list
3. Closed bugs automatically excluded (filtered in code)
4. New bugs from Jira automatically added
5. Updated bugs from Jira overwrite previous data

### Manual vs. System Data

**System-managed columns (overwritten each sync):**
- A-V: All bug data fields (ID, Title, Priority, Status, etc.)
- W: SYNCED timestamp

**Manual columns (preserved across syncs):**
- NONE - entire dataset is replaced

**Recommendation for preservation:**
If manual notes need to survive syncs, add a trigger to:
1. Save column NOTES to a separate archive sheet
2. Reapply after sync
3. Or add a "Manual Notes" column outside the clear range

## 7. REFRESH FLOW & TIMING

### Refresh Sequence (refreshDashboard)

```
1. getModuleList_(ss) → Get all active modules from Config
2. For each active module:
   a. pullModuleData_(mod) → Read module's Summary sheet
   b. Extract: WEB KPI, API KPI, SMOKE metrics, PERF results, etc.
3. writeOverview(ss, allData) → Aggregate to Overview tab
4. writeBugs(ss, allData) → Aggregate to Bugs tab (no Jira here, local data only)
5. refreshVAPTData() → Pull VAPT findings (if configured)
6. writeSmoke(ss, allData) → Aggregate smoke metrics
7. writeFailureScenario(ss, allData) → Pull failed/blocked test cases
8. writeCoverage(ss, allData) → Calculate coverage per submodule
9. appendHistory(ss, allData) → Snapshot for trend tracking
10. updateRaw(ss, allData) → Update internal cache
11. updateConfig(ss, allData) → Back-fill Project/Module/Submodule/PIC QA auto-fields
```

**Trigger Options:**
- Manual: `refreshDashboard()` menu button
- Auto: `setupAutoRefreshTrigger()` - time-based (default 10 minutes)
- Sequential: `refreshDashboardWithJiraSync()` - Jira Sync → Dashboard Refresh

## 10. SUMMARY: DUPLICATE PREVENTION STRATEGY

### Current Mechanism: FULL DATA REPLACEMENT

**Pros:**
- Simplest implementation
- Always in sync with Jira source of truth
- Handles status changes automatically
- No stale data

**Cons:**
- Loses any manual edits to bug rows
- No preservation of historical data
- Full re-fetch every sync (uses API quota)

### Recommended Enhancement for Duplicate Prevention

If you need to add incremental sync:

1. **Use Jira Key as unique identifier** (already done)
2. **Check before insert:**
   ```javascript
   const existingKey = bugSh.getRange(5, BUG_START_).getValue().find(r => r[JIRA_KEY] === key);
   if (existingKey) {
     // Update existing row
   } else {
     // Insert new row
   }
   ```
3. **Track sync state in a helper column:**
   - Column SYNCED: timestamp of last sync
   - Column LAST_JIRA_UPDATE: last update date from Jira
   - Skip rows where Jira update < last sync

4. **Add a "changelog" sheet:**
   - Log all changes (created, updated, closed)
   - Preserve historical audit trail
   - Useful for reporting

## 11. NEXT STEPS FOR YOUR IMPLEMENTATION

Based on this analysis, when implementing your feature:

1. **Use Config Sheet as Single Source of Truth (SSOT)**
   - Read active modules from Config
   - Metadata: project, module, submodule, team, Jira config

2. **Follow Existing Integration Patterns**
   - Use UrlFetchApp with Basic Auth
   - Store credentials in Credentials sheet
   - Use logging for debugging

3. **Leverage Existing Duplicate Prevention**
   - Jira Key is the unique identifier
   - Full data replacement (no merge needed)
   - Closed bugs are automatically filtered

4. **Consider Data Preservation**
   - Current system overwrites all bug data each sync
   - If you need historical tracking, add separate columns
   - Use _Raw sheet for internal caching

5. **Use Time-Based Triggers**
   - Follow the `setupAutoRefreshTrigger()` pattern
   - Create triggers only after validation
   - Always provide cleanup (removeJiraTriggers)
